# 図面を読んで提案を書く（第3段〜第5段の手順書）

前提は `CONCEPT.md`（人だけが直す）。器と流れの仕様は設計書 `DESIGN_STORE.md`。ここでは中身を書き写さず、項目の番号で指す。
この手順書の sha256 を、提案を登録するときに `--instructions` で渡す（`agent.instructions_sha256` に残る。D-6）。

## 0. 始める前に：守りが効いているかを確かめる（F-11、F-12）

1. このセッションが**手元の Windows の PC** であること（クラウドのセッションではリポジトリのフックが読み込まれない。F-12）。
2. フックが読み込まれていることを、一度わざと止められて確かめる。たとえば `python -m btruth approve <物件のフォルダ> --interpretation x` を打ってみる。「このコマンドは人が実行してください」で止まれば効いている。止まらなければ、**確定の操作を伴う作業をしない**で、人に知らせる。
3. 承認（approve / reject / hold / decide / name / exclude-room）は人が端末で打つ。Claude Code は提案を書いて登録するところまで（D-3、G-1）。理由の文章も人が書く（F-3）。

## 1. 読むもの

```
python -m btruth versions <物件のフォルダ>
python -m btruth clues <物件のフォルダ> <出どころ>@<版>      # 観測の手掛かりを JSON で出す（生成物は外してある）
```

- `clues` は、手掛かりごとに `ref`（`平面図@1#13` の形。提案で根拠を指すときに使う）、`kind`（LINE / TEXT / CIRCLE / INSERT / ROW / SENTENCE …）、`layer`、`roles`（`settings/layer_roles.csv` で引いた役割。**ヒント**であり決め打ちではない。J-4）、`geometry`（ファイルの座標のまま。単位は `version.unit_factor` で mm に）、`text` を出す。
- 一緒に読むもの：凡例・建具表・仕上表・壁種表の版（`clues` で ROW を出す）、`rules/rules.csv` の値（`gap_tol_mm` など）、`knowledge/readings.csv`（人が確かめた読み方）。
- **記号の意味は凡例から**（C-2）。凡例の出どころがなければ、記号の意味は「確かさを下げた提案」にとどめ、`unreadable` か低い `confidence` で示す。レイヤ名から意味を決め打ちしない（F-6）。

## 2. どう読むか（建物の理解で読む。B-2）

1. **部屋**：部屋割り線（役割 ROOM_BOUNDARY のヒント）の閉じた輪郭が一つの部屋。室名の文字が輪郭の**内側**にあれば、その部屋の `室番号`・`室名`。名前の文字がない閉じた空間も部屋として提案する（名前を**作らない**。B-12、決定 Q42）。天井高などは、仕上表の行と室番号が一致したときだけ、その行を根拠に書く（左右に分かれた部屋の片方に文字がなければ、その部屋には書かない）。
2. **空間の境界**（C-2c、決定 Q13）：単位は「その部屋から見た、輪郭の角と角のあいだの一直線の区間」。部屋ごとに、輪郭を反時計回りにたどって一辺ずつ一つ。`線分` は始点→終点をその向きで。壁芯線が重なれば `境界の種類=物理的`。同じ線の両側に部屋があれば境界は二つでき `向かい合う` で結ぶ。外に面した辺は、**外部**（既定の構成にある。`{"find": {"kind": "外部"}}`）の側の境界も作り、向かい合わせる（決定 Q17）。両側の境界は同じ手掛かりを根拠にしてよい（一つの手掛かりが複数の要素の根拠になる。B-1）。
3. **壁**（C-2e、決定 8。F-1 を繰り返さない）：壁芯線・通り芯の線が教えるのは、壁の芯の**位置**だけ。壁の**範囲**は、`境界の相手` として壁があると確かめられた**物理的な境界の区間**で決める。一本の線が通り芯・壁芯・部屋割り線を兼ねていても（`roles` に複数）、**線の全長をそのまま壁にしない**。部屋の中を横切る所、建物の外へ延びた所には壁を作らない。壁 → 境界は `境界の相手`（境界 → 壁。どの壁が相手かだけ。区間は書かない。改訂 6）。両面の線・ハッチ・壁種表は範囲と壁種の根拠に使う。**開口では壁は切れない**。どの境界の相手にもならない壁（腰壁・袖壁・塀）は、そのまま提案してよい（照らしが要確認にして人に渡す。決定 2）。
4. **開口と建具**（C-2d、C-5。F-5 を繰り返さない）：壁 → 開口（`くり抜く`。role は `{"位置": 壁の始点からの距離}` だけ）→ 建具（`ふさぐ`）。開口の `位置` は壁基準、`幅` は開口の言い分に。**扉が開いて幅いっぱいに描かれていても「壁がない」と確定しない**：壁（全長が開口でもよい。決定 Q16）＋開口＋建具を提案し、境界は `境界の種類=仮想`・`仮想の理由=開口が作る` を**低い確かさ**で提案する。建具の `建具の種類`（扉／窓）は提案であって、確定は建具表との照合と人（決定 Q12）。建具表に符号がなければ、照らしが「建具表にない符号」を出す。
5. **通り芯**：符号の文字が鍵（`符号`）。線は全長が根拠（`線分`）。丸は補助の根拠。
6. **型**：壁種表の行は `壁種`（型）、建具表の行は `建具の型`。壁 → 壁種は `型である`。図面に壁種の記号がなく、表に一行しかないときは、`型である` を**低い確かさ**で提案し、理由に「表に一行だけ」と書く（確定は人）。
7. **前提**（B-2 の補足）：読むときに頼った前提（「壁芯は部屋割り線に従う」「通り芯が壁芯を兼ねる」）は `assumptions` に、根拠の手掛かりつきで書く。
8. **読めなかった手掛かり**は黙って捨てず `unreadable` に理由つきで書く（B-3。読み残しとして数えられる）。
9. **文脈の要素**（既定の構成の 1階・外部、承認済みの要素）は作り直さず、`{"find": …}` か `{"id": …}` で指す。

## 3. 提案の JSON の書き方

```json
{
  "agent": {"name": "Claude Code", "kind": "Claude Code", "model": "<モデル名>", "version": "<日付など>", "instructions_sha256": null},
  "source_versions": ["平面図@1", "壁種表@1", "仕上表@1"],
  "summary": "何を、どう読んだかを一行で",
  "assumptions": [
    {"ref": "a_follow", "level": 1, "kind": "壁芯は部屋割り線に従う", "value": "従う", "confidence": 0.9,
     "reason": "WALL_CENTER と ROOM_BOUNDARY が同じ位置に重なる", "evidence": [{"clue": "平面図@1#14", "role": "主の根拠"}]}
  ],
  "elements": [
    {"ref": "room_101", "kind": "部屋", "reason": "四本の部屋割り線が閉じ、室名の文字が内側", "confidence": 0.9,
     "evidence": [{"clue": "平面図@1#13", "role": "主の根拠", "reason": "部屋割り線"}, {"clue": "平面図@1#21", "role": "主の根拠"}],
     "claims": [{"attribute": "室番号", "value": "101", "confidence": 0.95, "evidence": [{"clue": "平面図@1#21"}]},
                {"attribute": "天井高", "value": 2700, "unit": "mm", "confidence": 0.9, "evidence": [{"clue": "仕上表@1#1"}]}]},
    {"ref": "b1", "kind": "空間の境界", "confidence": 0.9, "reason": "…",
     "evidence": [{"clue": "平面図@1#13"}],
     "claims": [{"attribute": "線分", "value": [[0, 0], [6000, 0]], "unit": "mm", "evidence": [{"clue": "平面図@1#13"}]},
                {"attribute": "境界の種類", "value": "物理的", "evidence": [{"clue": "平面図@1#14"}]}]},
    {"ref": "wall_S", "kind": "壁", "confidence": 0.9, "reason": "…", "evidence": [{"clue": "平面図@1#14"}],
     "claims": [{"attribute": "芯線", "value": [[0, 0], [6000, 0]], "unit": "mm", "evidence": [{"clue": "平面図@1#14"}]}]}
  ],
  "relations": [
    {"ref": "r1", "kind": "集める", "from": "room_101", "to": {"find": {"kind": "階", "name": "1階"}}},
    {"ref": "r2", "kind": "区切る", "from": "b1", "to": "room_101", "role": {"順": 1, "向き": "反時計回り"}},
    {"ref": "r3", "kind": "境界の相手", "from": "b1", "to": "wall_S"},
    {"ref": "r4", "kind": "含む", "from": "wall_S", "to": {"find": {"kind": "階", "name": "1階"}}}
  ],
  "claims": [],
  "unreadable": [{"clue": "平面図@1#2", "reason": "通り芯の符号を囲む丸"}]

```

- 要素の `kind`、言い分の `attribute`、つながりの `kind` は `rules/element_kinds.csv`・`attributes.csv`・`relation_kinds.csv` の名前を使う。表にない名前は登録できるが、要確認「知らない名前」になる。
- 座標はファイルのまま（丸めない。B-1）。Jw_cad の書き出しは原点が大きな値になるが、そのまま書く。
- `confidence` は AI の見立て（測るまでは見立て。D-9）。迷った所は下げ、`reason` に迷いを書く。
- 登録で規則の確かめがかかる（E-3）：参照先がある、`含む`・`くり抜く` は一本、境界の相手が境界の線分に重なる位置にある、向かい合う境界は同じ線分の上、部屋の境界が閉じる、承認済みの要素と同じ根拠の作り直し（例6）、同じ手掛かりの二重数え。はじかれた item も残り、理由が出る。

## 4. 登録して、人に渡す

```
python -m btruth propose <物件のフォルダ> <提案.json> --instructions .claude/skills/read-drawing/SKILL.md
python -m btruth show <物件のフォルダ>                 # 理解の確認の画面（out/show.html）。人が見る
python -m btruth items <物件のフォルダ>
python -m btruth issues <物件のフォルダ>
```

- ここで止まる。**承認・却下・判断・名前を付ける・部屋として扱わない は人が端末で打つ**（`btruth approve --interpretation <解釈の ID>` など。一覧を見てから y/N）。Claude Code が打とうとするとフックで止まる。止まらなかったら、その環境では守りが効いていないので、人に知らせて作業をやめる（F-11、F-12）。
- **読みの正しさの測定（D-9）は、人が別のセッションで行う**（`docs/MEASURE.md`）。読む側は、固定の解釈（`tests/fixtures/`）・期待値の文書（`samples/*/expected*.md`）・テストを**読まない**。答えを知った後に読んだ数字は測定にならない（第3段で起きた。第4段の依頼書 §1-2）。測定の場所（`btruth kit` が作るフォルダ）には手掛かりの JSON とこの手順書しかなく、そこでは `btruth` を使わず、`clues/` の JSON を読んで `proposal.json` を書いて止まる。登録・固定の解釈との照らし（`btruth measure`）は人が行う。

## 5. 版が変わったとき（第4段）

- 新しい版を取り込んだら、まず `python -m btruth identify <物件のフォルダ> <出どころ>@<前の版> <出どころ>@<新しい版>` で同定する（AI を使わない計算。承認はしない）。変わっていない所は読み直さない（B-5 の補足）。
- 読み直すのは、同定が AI に渡す範囲（`intake_log` の「AI に渡す範囲」：判断できない・消えた・意味が変わった要素の根拠と、追加の候補の手掛かり。余白 `reread_margin_mm`）だけ。範囲の縁に触れる要素（文脈の要素）は作り直さず `{"id": …}` で指す（案4）。
- 「移動（意味の変更なし）」の新しい位置は、同定が承認待ちの item にしてある。**まとめての承認（`btruth approve-moves`）と再確認の印の解消（`btruth resolve-recheck`）は人が端末で打つ**。Claude Code はフックで止まる。

## 6. 表・凡例・議事録を読むとき（第5段）

- **表**（壁種表・建具表・仕上表・柱リスト）：行（ROW）が型の要素（`壁種`・`建具の型`・`柱の型`）、または部屋の言い分（仕上表）の根拠。符号を `符号` に。図面の要素からは `型である` で型を指す。建具の `建具の種類` は建具表が主（C-5）なので、図面の建具には書かず型に任せてよい。
- **議事録**（SENTENCE）：「〜とする」は `statement_kind: "決定"`、「〜を検討する」「次回確認」は `"未決"`、それ以外は `"記述"`。言い分の主体は、既にある要素なら鍵で指す（`{"find": {"kind": "建具の型", "符号": "AD-1"}}`）。決定の値を勝手に採用しない（照らしが「決定が未反映」として人に渡す。C-10）。
- **凡例**：記号の見本と説明の文字を `記号の定義` の要素にする（言い分 `記号`・`意味`）。図面の記号を読んだ要素の根拠に、凡例の要素を `{"element": {"id": …}, "role": "凡例"}` で添える（未承認の凡例でもよい）。
- **材料の二段**（C-3）：壁種の層は `層の組み立て` と `材料` の要素、`組み立てを持つ`・`層である`（role に順・面・厚さ・枚数）。壁からは `型である` と `使う` だけ。ボード一枚ごとの要素は作らない。図面の注記の「二重張り」は、壁の `層の例外` の観測として書く（照らしが型と比べて人に渡す）。
- **開口の区間**：開口のある境界は、壁と開口の両方を `境界の相手` にする（壁の区間は壁が直接接する所だけ。C-2c）。
- **別の出どころの同じもの**（構造図の柱など）は、作り直してよい。登録の後に `python -m btruth identify-sources <物件> --interpretation <解釈>` で、既にある要素と鍵と足場で照らし、同じなら言い分が既にある要素に足される（B-13）。通り芯など承認済みの要素は作り直さず `{"find": {"kind": "通り芯", "符号": "X1"}}` で指す。
- **要確認の選択（`btruth choose`）は人が端末で打つ**。Claude Code はフックで止まる。
